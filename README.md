# 复扫页数核对页

古籍复扫验收用的网页工具：导入「批次修订清单」与「页数汇总单」，勾选待验
批次后，只在**整单组合**严格覆盖所选批次时给出总页数；组合之间总页数不同
则列出分歧的两组单号与合计；没有有效组合则明确提示无法出数。同批入库、需要
分开补扫的批次可在核对页**拆批**，旧汇总单无需重开即可继续使用。

## 规则如何落地

- **整单计入**：一张汇总单要么整张采用，要么整张不用；不接受按批次拆分。
- **恰好一次**：每个所选批次在组合中恰好出现一次，且组合中不能含任何未选
  批次（多出来的批次会让整张单失去资格）。
- **有效组合**：只有「所含批次修订号全部等于现行修订号」的单才可参与组合；
  含未知批次、单内重复批次的单在导入时即拒绝。
- **报数**：所有有效组合总页数一致 → 报该数；不一致 → 报分歧，给出最小和
  最大两组（单号 + 各自合计），不报单一数字；无有效组合 → 无法出数。
- **拆批**：核对页选择一个现行（叶子）批次，填两个不同的新编号，编号自最近
  一次整套导入起未被任何批次使用过。两个子批沿用原修订号，之后可分别更版、
  也可再拆；每次拆批另存一次提交。拆批后批次数仍受 16 批上限约束，所据提交
  已过期（被别的提交抢先）或保存失败时整笔回滚，现行数据保持原状。
- **旧单随拆批展开**：汇总单始终按**原批次号、原修订号**存档。核对时原批次
  沿批次谱系展开到它的所有现行后代；只有这些后代的现行修订**全部**与单上的
  原修订吻合，整张单才可用。网页在汇总单表格并排显示「单上原批次」与它目前
  覆盖的批次。
- **不能给单个子批报整单合计**：拆批后一张单的覆盖是若干叶子批次；只勾选
  其中一个子批时，该单因含未选批次而失去资格，页面提示无法出数。
- **整套重导重置谱系**：整套导入按新清单与新单核对，即使重用了历史批次号；
  上次导入以来的编号占用记录也随之清空，旧编号可再次使用。
- **同一次已提交状态**：每次导入、更版或拆批都追加一个不可变快照
  （`submissions` 行 + 该提交号下的批次/汇总单/批次谱系行）。核对在一个
  SQLite 读事务里按同一个提交号取清单、谱系与汇总单，并在写事务中确认该提交
  号仍是最新提交，杜绝跨状态混读。更版时汇总单原样复制进新快照，仍记录旧
  修订号，于是自动变为「不采用」。
- **上限**：最多 16 个批次、40 张汇总单；解析层、仓储层与 SQLite 触发器三处
  都做了限制。
- **旧库免重导**：启动时自动迁移旧版数据库——新增 `batch_lineage` 表，并把
  带批次外键的 `sheet_entries` 原地重建（数据保留、迁移可重复执行）。

## 运行

### Docker Compose（交付方式）

```bash
docker compose up --build
# 打开 http://127.0.0.1:8000
```

数据落在命名卷 `collation-data` 的 `/data/collation.sqlite3`，容器以非 root
用户运行，带健康检查。

### 本机直接跑

```bash
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
DATABASE_PATH=./data/collation.sqlite3 gunicorn --bind 127.0.0.1:8000 wsgi:app
```

### 测试

```bash
pip install -r requirements-dev.txt
python -m pytest
```

### 联机演示

服务启动后：

```bash
python3 demo/demo.py http://127.0.0.1:8000 demo/out
python3 demo/demo_split.py http://127.0.0.1:8000 demo/out-split
```

脚本只走 HTTP：

- `demo/demo.py`：导入 → 核对得 240 页 → 把 B01 更版到 r3（旧单失效、无法
  出数）→ 重新导入吻合单 → 再导入一张同覆盖不同合计的单，核对应报分歧。
- `demo/demo_split.py`：导入合计单 → 把 B01 拆成 B01A/B01B → 全部叶子一起
  核对仍报原合计、只选一个子批则无法出数 → 给 B01A 单独更版使旧单失效 →
  整套重导（重用批次号）后按新清单恢复核对。

记录写入各自输出目录的 `transcript.md`，关键响应 HTML 也一并保存。

## 输入格式

批次清单，每行一个批次：

```
B01 r2
B02, rev3
B03 修订=1
```

汇总单用**空行**分隔；每张首行是 `单号 总页数`，其后每行 `批次 修订号`：

```
S1 150
B01 r2
B02 r2

S2 90
B03 r1
B04 r1
```

`#` 开头的整行是注释。汇总单若没有空行分隔，第二张的「单号 页数」会被当
成上一张的批次行；导入前的交叉校验会以「批次清单中不存在」报错拦截，不会
静默错并。

## 验证结果（据实）

- `python -m pytest`：**72 项全部通过**。原有 40 项（解析、仓储、并发、Web、
  600 组随机差分）零回归；新增 32 项覆盖拆批仓储规则、谱系展开核对、拆批
  Web 流程、旧库迁移与 400 组带谱系的随机差分。
- 拆批专项实测（gunicorn 多 worker，纯 HTTP，见 `demo/demo_split.py`）：
  拆批后全部叶子一起核对仍报原合计；只选一个子批无法出数；子批单独更版后
  旧单整张不采用并给出原因；整套重导重用批次号后谱系重置、核对恢复。
- 旧库迁移：用旧版 schema（`sheet_entries` 带批次外键、无 `batch_lineage`）
  手工建库后启动应用，数据完整保留且无需重导即可拆批；迁移重复执行幂等。
- 16 批上限：15 批拆到 16 批成功，再拆到 17 批被拒且现行数据不变；解析层、
  仓储层与 SQLite 触发器三处限制仍在。
- 并发：同一基准提交上的两个并发拆批只有一个成功、另一个被拒
  （`tests/test_concurrency.py`）；保存中途失败时整笔回滚。
- 用**生产依赖**（`requirements.txt`：Flask 3.1.3 + gunicorn 23.0.0；本机
  沙箱实际安装 gunicorn 27.0.1）实跑 gunicorn 并完整跑通两个 demo 脚本。
- 已修正的实现问题（本次）：拆批克隆快照时漏带批次谱系导致更版报错；
  `sheet_entries` 的批次外键会阻止单据保留已拆批次号，已随迁移移除；
  快照交叉校验原先只认叶子批次，已把谱系父节点纳入合法批次。

## 剩余事项

- 无鉴权、无审计人字段；页面面向内网验收台，若需多人使用应加登录与操作人。
- 只支持手工粘贴/表单导入，未接扫描系统导出文件；格式若要扩展需同步改
  `app/parsing.py`。
- 拆批目前是「一拆二」；若业务需要一拆多，需要同步调整表单、谱系校验与
  测试（核对引擎本身支持任意分叉的谱系）。
- 提交历史只展示最近 8 条，未提供“回滚到某次提交”的入口（数据已保留，可
  后续加只读回看）。
- 超大汇总单（接近 40 张、每张覆盖大量批次）时采用 2^16 状态 DP；当前上限
  下性能已测，但若上限提高需重新评估。
